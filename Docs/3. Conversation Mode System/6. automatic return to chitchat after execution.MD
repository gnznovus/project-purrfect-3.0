# Automatic Return to Chitchat After Execution

## Purpose

This document defines how Purrfect handles conversation state after an execution workflow completes.

The goal is to:

- Prevent users from being stuck inside Planner mode.
- Cleanly close completed tasks.
- Return the conversation naturally back to normal interaction.
- Preserve completed task information without keeping active workflow state.

---

# Core Rule

Successful execution completion automatically returns the conversation to Chitchat mode.

Execution completion represents the end of the active planning workflow.

Planner should not remain active after a task has finished.

---

# Successful Execution Flow

```text
Planner
    ↓
Execution Layer
    ↓
Execution Completed
    ↓
Clear Active Task State
    ↓
Return to Chitchat
```

State after successful completion:

```text
mode = chitchat
active_task_id = none
```

---

# Why Return Automatically?

Keeping Planner active after completion creates unnecessary friction.

Example:

```text
User:
Plan my vacation.

↓

Planner gathers information.

↓

Execution:
Calendar event created successfully.

↓

User:
Thanks!
```

Expected behavior:

```text
Chitchat:
You're welcome!
```

The user should not need to manually exit a completed workflow.

---

# Execution Result Handling

The Execution Layer reports completion through a structured result.

Example:

```json
{
  "status": "completed",
  "execution_id": "execution_xxx",
  "result": "Calendar event created"
}
```

The Conversation Mode System uses this result to determine whether the workflow has completed.

Execution does not directly change conversation mode.

---

# Failure Handling

## Recoverable Failure

A recoverable failure is a situation where the task can continue after additional information or correction.

Example:

```text
Execution:
Calendar creation requires timezone information.
```

Flow:

```text
Execution
    ↓
Planner
    ↓
Request missing information
    ↓
Continue execution
```

The active task remains.

---

## Non-Recoverable Failure

A non-recoverable failure means the current workflow cannot continue.

Example:

```text
Execution:
External provider unavailable.
```

Possible flow:

```text
Execution
    ↓
Planner
    ↓
Inform user
    ↓
Cancel active task
    ↓
Return to Chitchat
```

The exact recovery strategy depends on task importance and available alternatives.

---

# Post-Execution Conversation

After returning to Chitchat:

- New messages are treated as normal conversation.
- Previous task information remains available through Memory.
- New task signals follow the normal Planner delegation flow.

Example:

```text
User:
What did we schedule earlier?
```

Flow:

```text
Chitchat
    ↓
Memory Retrieval
    ↓
Answer user
```

The system does not reactivate Planner unless a new planning request occurs.

---

# State Boundary

Successful completion clears active workflow state.

Cleared:

- active_task_id
- current planning session state

Preserved:

- Conversation history
- Execution history
- Task memory
- Relevant user memories

---

# Design Principles

- Execution completion automatically returns users to normal conversation.
- Execution Layer reports results but never controls conversation modes.
- Planner owns active task state only while planning is active.
- Memory preserves historical information without keeping workflows alive.
- Completed tasks should feel finished, not paused.
