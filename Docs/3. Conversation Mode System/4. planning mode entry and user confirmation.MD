# Planning Mode Entry and User Confirmation

## Purpose

Planning Mode Entry defines how Purrfect transitions from normal conversation into Planner mode.

The purpose is to:

- Prevent unexpected agent handoffs.
- Keep the user aware when a specialized planning workflow will begin.
- Maintain clear responsibility boundaries between agents.
- Ensure that Planner activation is always intentional.

Planner mode is never activated automatically.

---

# Entry Principle

Entering Planner mode always requires explicit user confirmation.

Task detection, user requests, or LLM suggestions can only trigger a **Planner delegation request**.

They cannot directly change the conversation mode.

```text
User
    ↓
Chitchat Agent
    ↓
Planner Entry Check
    ↓
Delegation Request
    ↓
User Confirmation
    ↓
Planner Mode
```

---

# Planner Entry Sources

There are two possible sources that can trigger a Planner delegation request.

---

## Task Signal Detection

The Chitchat Agent detects that the current conversation may benefit from planning.

Example:

```text
User:
I need to prepare a birthday party.

Chitchat Agent:
task_signal = true
```

Flow:

```text
Chitchat
    ↓
Task Signal Detection
    ↓
Conversation Mode System
    ↓
Planner Delegation Request
    ↓
User Confirmation
    ↓
Planner
```

Task signals are only suggestions.

They never directly activate Planner.

---

## Explicit Planning Request

The user directly requests planning assistance.

Examples:

- "Help me plan my trip."
- "Organize my schedule."
- "Create a plan for this."

Even explicit requests still pass through the same delegation gate.

Flow:

```text
Chitchat
    ↓
Planning Request Detected
    ↓
Conversation Mode System
    ↓
Planner Delegation Request
    ↓
User Confirmation
    ↓
Planner
```

This keeps all Planner entry paths consistent.

---

# Planner Delegation Request

The user should not see internal system concepts such as conversation modes.

Avoid:

> "Switching from Chitchat mode to Planner mode."

Instead, communicate the agent handoff.

Examples:

> "Got it. Would you like me to hand this over to the Planner Agent to organize this?"

> "I can help organize this. Should I bring in the Planner Agent?"

The user is confirming delegation, not a technical state transition.

---

# User Confirmation Handling

## Accepted

Example:

```text
User:
Yes, do it.
```

Flow:

```text
Confirmation Accepted
        ↓
Conversation Mode = Planner
        ↓
Create active_task_id
        ↓
Initialize Planner Context
        ↓
Planner takes control
```

---

## Rejected

Example:

```text
User:
Nope, just chatting.
```

Flow:

```text
Confirmation Rejected
        ↓
Remain in Chitchat
        ↓
Record planner_prompt_declined
        ↓
Continue conversation
```

The system should avoid repeatedly offering Planner during the same conversation context.

---

## Ambiguous Response

Examples:

- "Maybe."
- "Not sure."
- "Later."

Flow:

```text
Ambiguous Response
        ↓
No transition
        ↓
Remain Chitchat
```

The system must never assume acceptance.

Only clear confirmation activates Planner.

---

# Pending Transition State

Planner entry confirmation does not create Planner state.

Before confirmation:

```text
mode = chitchat
active_task_id = none
```

After confirmation:

```text
mode = planner
active_task_id = created
```

The confirmation stage is only a temporary interaction step.

No planning memory, task state, or execution context should be created before acceptance.

---

# Core Rules

- Planner mode entry always requires explicit user confirmation.
- Task signals only create Planner offers.
- Explicit planning requests still pass through the delegation gate.
- Only the Conversation Mode System can change conversation modes.
- Agents can suggest transitions but cannot perform them.
- The user confirms delegation to Planner, not an internal mode switch.
- Ambiguous responses never activate Planner.
- Rejected Planner offers should respect planner suggestion suppression behavior.

---

# Design Philosophy

Purrfect should never surprise the user by changing workflows unexpectedly.

The system should behave like a team of assistants:

```text
Chitchat Agent
    ↓
"Should I ask the Planner Agent to help?"
    ↓
User decides
    ↓
Planner Agent
```

The user remains in control of when specialized workflows begin.
