# Planning Acceptance and Rejection Behavior

## Purpose

This document defines how Purrfect handles user responses after requesting permission to delegate a conversation to the Planner Agent.

The goal is to ensure:

- Planner activation is intentional.
- User remains in control of workflow transitions.
- Rejected planning offers do not create unnecessary task state.
- Future planning requests remain possible.

---

# Acceptance Behavior

When the user accepts Planner delegation, the Conversation Mode System starts the planning workflow.

Example:

```text
Purrfect:
Would you like me to hand this over to the Planner Agent?

User:
Yes.
```

Flow:

```text
Confirmation Accepted
        ↓
Conversation Mode = Planner
        ↓
Create active_task_id
        ↓
Build Planner Context
        ↓
Planner Agent Starts
```

---

# Planner Initialization

The acceptance event is the only point where Planner state is created.

Before acceptance:

```text
mode = chitchat
active_task_id = none
```

After acceptance:

```text
mode = planner
active_task_id = created
```

No task state, planning memory, or execution context should exist before acceptance.

---

# Planner Context Handoff

When entering Planner mode, the Planner Agent receives relevant context.

Example:

```json
{
  "initial_request": "I want to prepare a birthday party",
  "conversation_context": "...",
  "task_signal": true
}
```

Planner may receive:

- Original user request.
- Relevant conversation context.
- Relevant memory.
- Task signal information.

Planner does not need internal detection details.

Planner does not decide whether the transition should happen.

---

# Rejection Behavior

When the user rejects Planner delegation, the system remains in Chitchat mode.

Example:

```text
Purrfect:
Would you like me to hand this over to the Planner Agent?

User:
Nope, just chatting.
```

Flow:

```text
Confirmation Rejected
        ↓
Remain Chitchat
        ↓
Do not create active_task_id
        ↓
Record planner_prompt_declined
        ↓
Continue Conversation
```

---

# Rejection Meaning

A rejection means:

> The user does not want to enter Planner mode at this moment.

It does not mean:

- The user permanently disables Planner.
- The user never wants planning assistance.
- The system should forget future planning capability.

Planner remains available through explicit user requests.

---

# Rejection Scope

Rejected Planner offers only affect automatic Planner suggestions.

Example:

```text
User:
I want to visit Japan.

Purrfect:
Would you like me to hand this over to the Planner Agent?

User:
Nope.
```

Later:

```text
User:
I also want to visit Spain.
```

Purrfect should avoid repeatedly offering Planner during the same conversation context.

This behavior is controlled by:

- planner_prompt_declined
- conversation_topic
- topic_refresh_ttl

---

# Explicit Planning Request After Rejection

A previous rejection must never block explicit planning requests.

Example:

```text
User:
Nope, just chatting.

...

User:
Actually, help me plan the trip.
```

Flow:

```text
Explicit Planning Request
        ↓
Ignore Previous Suppression
        ↓
Planner Delegation Request
        ↓
User Confirmation
        ↓
Planner
```

The user can always manually enter Planner mode.

---

# Ambiguous Responses

Responses without clear acceptance should not activate Planner.

Examples:

- "Maybe."
- "Not sure."
- "Later."
- "I don't know."

Behavior:

```text
Ambiguous Response
        ↓
Remain Chitchat
        ↓
Do not create Planner State
```

Ambiguous responses may require future refinement.

---

# Task State Protection

Acceptance and rejection are conversation events, not tasks.

Before acceptance:

```text
No active task exists.
```

After acceptance:

```text
Task lifecycle begins.
```

This prevents abandoned planning attempts from creating unnecessary memory or execution records.

---

# Core Rules

- User acceptance is required before entering Planner mode.
- Acceptance creates Planner state.
- Rejection keeps the system in Chitchat mode.
- Rejection only affects proactive Planner suggestions.
- Explicit planning requests override previous rejection.
- Ambiguous responses never activate Planner.
- Planner state should not exist before user acceptance.
- Only the Conversation Mode System controls the transition.
