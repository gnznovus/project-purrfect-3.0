# Active Planning State Across Multiple Turns

## Purpose

Planner workflows are not limited to a single request-response interaction.

Many tasks require multiple conversation turns to:

- Collect missing information.
- Refine user requirements.
- Build a plan.
- Validate the plan.
- Prepare execution.

The Active Planning State allows Purrfect to maintain continuity during an ongoing planning workflow.

Without this state, every user message would be treated as an isolated request, similar to the original Purrfect 2.0 intent classification approach.

---

# Ownership

Active Planning State belongs to the Planner workflow.

The responsibility is separated between systems.

## Conversation Mode System

Maintains only high-level state:

```text
Conversation State
├── mode
│   └── planner
│
└── active_task_id
```

The Conversation Mode System knows:

- Planner is active.
- Which task is currently active.

It does not store planning details.

---

## Planner Agent

Owns the active planning information.

Example:

```text
Active Task
├── task_id
├── objective
├── collected_information
├── missing_information
├── current_plan
└── execution_status
```

Planner is responsible for:

- Understanding the goal.
- Tracking gathered information.
- Identifying missing requirements.
- Building and refining the plan.

---

# Active Task Lifecycle

## Creation

Active planning state is created only after the user accepts Planner delegation.

Before acceptance:

```text
mode = chitchat
active_task_id = none
```

After acceptance:

```text
mode = planner
active_task_id = task_xxx
```

No active task exists before user confirmation.

---

## Multi-Turn Planning Flow

Example:

```text
User:
Help me plan my vacation.

↓

Planner starts.

↓

Create active_task_id
```

---

Planner identifies missing information:

```text
objective:
Plan vacation

missing_information:
- destination
- travel date
- budget
- travelers
```

Planner asks for required information.

---

User provides information:

```text
Japan, December, 2 people, around 50k THB.
```

Planner updates:

```text
collected_information:
- destination = Japan
- travel_date = December
- travelers = 2
- budget = 50k THB
```

The active task remains the same.

---

# Missing Information Collection

Planner should prefer collecting multiple missing information fields in a single request.

Preferred:

```text
To prepare this plan, I need:

- Destination
- Travel dates
- Number of travelers
- Budget range

Can you provide those details?
```

Avoid unnecessary one-question-at-a-time flows:

```text
Planner:
Where do you want to go?

User:
Japan.

Planner:
When?

User:
December.

Planner:
How many people?
```

---

# Required vs Optional Information

Planner should distinguish between:

## Required Information

Information needed to complete the task.

Example:

```text
Travel planning:

Required:
- Destination
- Travel date
```

---

## Optional Information

Information that improves the result but is not required.

Example:

```text
Optional:
- Food preference
- Hotel preference
- Activities
```

Planner should not overwhelm users by requesting every possible detail.

---

# Temporary Topic Changes

Users may temporarily leave the planning topic.

Example:

```text
Planner

User:
Before that, what's the weather tomorrow?
```

This should not automatically cancel planning.

Flow:

```text
Planner
    ↓
Answer temporary question
    ↓
Return to active planning task
```

The active task remains available.

---

# Task Completion

When planning is complete:

```text
Planner
    ↓
Validated Plan
    ↓
Execution or User Review
```

The active task continues until the workflow finishes.

After successful execution:

```text
Execution Completed
    ↓
Clear active_task_id
    ↓
Return Chitchat
```

---

# Task Cancellation

If the user cancels:

Example:

```text
User:
Actually forget it.
```

Flow:

```text
Planner
    ↓
Cancel active task
    ↓
Clear active_task_id
    ↓
Return Chitchat
```

The unfinished task may be handled by Memory in the future, but it is no longer an active workflow.

---

# Active State vs Memory

Active Planning State and Memory serve different purposes.

## Active Planning State

Represents:

> What are we currently working on?

Example:

```text
active_task_id = japan_trip_001
```

Temporary.

Exists only while the workflow is active.

---

## Memory

Represents:

> What happened in the past?

Example:

```text
User previously planned a Japan trip.
```

Persistent.

Used for future retrieval.

---

# Design Principles

- Planner owns active task details.
- Conversation Mode only tracks Planner activation.
- Active planning state exists only after user confirmation.
- Multiple conversation turns should contribute to the same task.
- Planner should collect missing information efficiently.
- Planner should avoid unnecessary questioning.
- Temporary side conversations should not destroy active planning state.
- Completed or canceled tasks should clear active state.
- Historical information belongs to Memory, not active planning state.

---

# Future Refinements

The following areas may evolve later:

- Persistent unfinished tasks across sessions.
- Advanced task memory.
- Adaptive questioning strategy.
- ML-based estimation of required information.
- More complex planning workflows.
