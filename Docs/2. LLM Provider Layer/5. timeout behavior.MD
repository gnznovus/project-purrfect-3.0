# Timeout Behavior

## Purpose

Timeout Behavior defines how Purrfect handles LLM provider requests that do not complete within an allowed time.

LLM requests must be bounded so that a provider that becomes unresponsive or excessively slow cannot indefinitely block the system workflow.

A timeout is treated as a provider failure and is handled through the defined retry and provider failure policies.

---

## Responsibility

Timeout Behavior is responsible for:

* Defining that LLM requests have bounded execution time.
* Detecting when an LLM request exceeds its allowed timeout.
* Terminating or cancelling the request when supported.
* Returning a normalized timeout failure.
* Preserving enough information for tracing and failure handling.

Timeout Behavior does not decide the overall workflow response after a timeout.

---

## Timeout Boundary

The general flow is:

```
Purrfect
    ↓
LLM Provider Interface
    ↓
Provider Adapter
    ↓
Provider
    ↓
Request exceeds timeout
    ↓
Timeout
    ↓
Normalized Timeout Failure
    ↓
Retry / Provider Failure Handling
```

The timeout applies to the individual LLM provider request.

Each LLM request must be independently bounded.

---

## Timeout Types

The architecture may distinguish different timeout conditions when the provider or transport layer exposes enough information.

Potential timeout conditions include:

* Connection timeout.
* Request timeout.
* Response timeout.
* Streaming inactivity timeout.

These conditions may be normalized into a common timeout failure while preserving the original failure classification as optional metadata.

The system should not require every provider to expose identical timeout information.

---

## Timeout Configuration

Timeout duration must be configurable.

The timeout may be determined by:

* Global provider defaults.
* Provider-specific defaults.
* Model-specific configuration.
* Request-specific requirements.

More specific configuration may override broader defaults when supported.

Timeout configuration must remain bounded and must not allow an individual request to wait indefinitely.

The initial MVP may use a simple configurable default timeout rather than introducing complex dynamic timeout calculation.

---

## Request Cancellation

When the underlying provider or transport mechanism supports cancellation, a timed-out request should be cancelled to prevent unnecessary continued processing.

Cancellation behavior is provider-dependent and remains inside the Provider-Specific Adapter or underlying transport layer.

Purrfect must not assume that every provider can immediately terminate server-side processing.

The system should distinguish between:

* Client-side request timeout.
* Provider-side processing termination.

A client-side timeout does not necessarily guarantee that the provider stopped processing the request.

---

## Timeout Result

A timed-out request must not be treated as a successful LLM response.

The provider layer returns a normalized timeout failure.

The normalized failure may include:

* Failure type.
* Provider.
* Model.
* Request identifier.
* Timeout duration.
* Elapsed time when available.
* Original provider or transport information when available.

The failure must remain traceable to the original request.

---

## Timeout Recovery

A timeout is considered a transient failure unless additional information indicates otherwise.

The recovery flow is:

```
LLM Request
    ↓
Timeout
    ↓
Retry Policy
    ↓
Retry Same Provider
    ↓
Retry Exhausted
    ↓
Compatible Provider / Model Failover
    ↓
Final Provider Failure Handling
```

Retry count, backoff, and provider failover are defined by their respective policies.

Timeout Behavior only identifies and reports the timeout condition.

---

## Timeout and Model Selection

A timeout does not automatically mean that the selected model is unsuitable.

A timeout may result from:

* Temporary provider load.
* Network conditions.
* Provider availability.
* Request complexity.
* Model processing time.

Model Selection / Routing may use historical timeout information as part of future routing decisions, but Timeout Behavior itself does not select another model.

---

## Timeout and Streaming

For streaming responses, timeout behavior may differ from a standard request.

A streaming request may be considered active while the provider continues producing output.

A streaming inactivity timeout may be used when no new response data is received within the configured period.

The system should not treat normal long-running generation as a timeout when the provider is actively producing valid output.

---

## Observability

Timeout events must be traceable through the system.

Relevant information may include:

* Request ID.
* Execution ID.
* Conversation ID.
* Provider.
* Model.
* Timeout type.
* Configured timeout.
* Elapsed time.
* Retry attempt.
* Final outcome.

This allows timeout failures to be distinguished from other provider failures during debugging and system evaluation.

---

## Responsibility Boundaries

Timeout Behavior owns:

* Timeout definition.
* Timeout detection.
* Request time limits.
* Timeout cancellation where supported.
* Normalized timeout reporting.
* Timeout-related tracing metadata.

Timeout Behavior does not own:

* Retry policy.
* Provider failover.
* Model selection.
* Model escalation.
* Workflow recovery.
* User-facing failure responses.
* Static fallback responses.
* Cost calculation.

---

## Architectural Principle

> **Every LLM provider request must have a bounded execution time. A request that exceeds its allowed timeout is treated as a failed request, never as a successful response.**

Timeout handling provides the failure signal.

Retry Behavior determines whether the request should be attempted again.

Provider Failure Handling determines whether the system should fail over or ultimately fail.

Higher-level components determine how the failure affects the user's workflow.
