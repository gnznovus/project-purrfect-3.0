# Model Configuration

## Purpose

Model Configuration defines the configuration and metadata Purrfect requires to identify, describe, and use an LLM model through the LLM Provider Layer.

Model configuration allows Purrfect to work with multiple models and providers without embedding model-specific assumptions throughout the application.

Model configuration describes what a model is and how it can be used.

It does not decide which model should be selected for a specific request.

---

## Responsibility

Model Configuration is responsible for defining:

* Model identity.
* Provider association.
* Model capabilities.
* Supported languages.
* Context limitations.
* Output limitations.
* Supported interaction capabilities.
* Default model parameters.
* Model availability status.
* Model-specific configuration required by the provider abstraction.

Model configuration must provide enough information for other system components to determine whether a model is suitable for a requested workflow.

---

## Model Identity

Each configured model must have a stable identity within Purrfect.

Model identity should distinguish between:

* Provider.
* Provider-specific model identifier.
* Purrfect model identifier.

The Purrfect model identifier provides an internal reference that allows the rest of the system to remain independent of provider-specific naming conventions.

A model configuration may therefore conceptually contain:

```
Provider
    ↓
Provider Model ID
    ↓
Purrfect Model ID
```

The provider-specific model identifier is used only where communication with the provider requires it.

---

## Model Capabilities

Model configuration must describe the capabilities supported by the model.

Initial capability metadata may include:

* Text generation.
* Multilingual understanding.
* Structured output.
* Tool calling.

Future capabilities may include:

* Vision.
* OCR.
* Multimodal input.
* Coding-specialized capabilities.
* Other specialized model capabilities.

Capability metadata allows the system to determine whether a model can satisfy the requirements of a particular request.

A model must not be selected for a workflow that requires capabilities the model does not support.

---

## Language Support

Model configuration must describe the languages supported by the model when that information is relevant to model selection.

Language support may include:

* Supported languages.
* Language quality or confidence metadata when available.
* Mixed-language support when relevant.

Language support is treated as model capability metadata.

The model configuration does not perform translation or language detection.

---

## Context Limits

Model configuration should describe the model's known context limitations.

This may include:

* Maximum supported context size.
* Maximum input size.
* Maximum output size.
* Other provider or model-specific context constraints.

Context Assembly uses this information when constructing requests.

The model configuration does not decide how context should be assembled or truncated.

---

## Output Limits

Model configuration may describe known output limitations.

Examples include:

* Maximum output tokens.
* Structured output support.
* Tool-call support.
* Provider-specific output constraints relevant to the common interface.

The configuration describes the model's capabilities and limitations.

The calling workflow determines the actual output requirements for each request.

---

## Default Model Parameters

Model configuration may define default parameters used when a request does not explicitly provide alternatives.

Examples may include:

* Temperature.
* Maximum output tokens.
* Sampling parameters.
* Other supported generation parameters.

These defaults must remain configurable.

The system must distinguish between:

* Model defaults.
* Request-specific parameters.
* Provider-specific parameters.

Request-specific requirements take precedence over model defaults when supported.

Provider-specific parameters must remain isolated from unrelated core components.

---

## Availability

Model configuration should provide a mechanism to represent whether a model is currently available for use.

A model may be:

* Enabled.
* Disabled.
* Temporarily unavailable.
* Deprecated.
* Experimental.

Availability information may be used by model selection and routing logic.

Temporary provider failures must not require permanently modifying the model's configuration.

---

## Configuration and Secrets

Model configuration may reference provider credentials or authentication requirements but must not store sensitive secrets directly as plain configuration metadata.

Provider credentials and secrets belong to the appropriate secure configuration or secret-management mechanism.

Model configuration should reference the required provider identity without owning secret storage.

---

## Model Configuration vs Model Selection

Model Configuration describes the model.

Model Selection / Routing decides which model should handle a specific request.

The separation is:

```
Model Configuration
    ↓
What can this model do?
    ↓
Model Registry
    ↓
Available model candidates
    ↓
Model Selection / Routing
    ↓
Which model should handle this request?
```

Model configuration must not contain request-specific routing decisions.

---

## Model Configuration vs Context Assembly

Model Configuration provides model constraints and capabilities.

Context Assembly uses those constraints when preparing a request.

For example:

```
Model Configuration
    ↓
Context Limit: X
Structured Output: Supported
Tool Calling: Supported
    ↓
Context Assembly
    ↓
Build compatible request
```

Context Assembly remains responsible for determining what the current request requires.

Model Configuration only describes what the selected model supports.

---

## Model Configuration vs Provider Adapter

Model Configuration describes the model independently of the provider's API implementation.

The Provider-Specific Adapter is responsible for translating the request into the provider's API format.

The separation is:

```
Model Configuration
    ↓
Model capabilities and constraints
    ↓
Context Assembly
    ↓
Common LLM Request
    ↓
Provider Adapter
    ↓
Provider API
```

Provider-specific implementation details must not be embedded into general model configuration unless they are required metadata for the provider abstraction.

---

## Responsibility Boundaries

Model Configuration owns:

* Model identity.
* Provider association.
* Model capability metadata.
* Language support metadata.
* Context and output limitations.
* Configurable model defaults.
* Model availability state.
* Non-secret model-specific configuration.

Model Configuration does not own:

* Model selection decisions.
* Request context assembly.
* Prompt construction.
* Agent reasoning.
* Tool execution.
* Execution authorization.
* Provider API communication.
* Provider-specific request translation.
* Retry behavior.
* Provider failover.
* Cost calculation.
* Secret storage.

---

## Architectural Principle

> **Model Configuration describes what a model is, what it supports, and what constraints apply to it. It does not decide when or why the model is selected.**

Model configuration provides the facts required by Context Assembly and Model Selection / Routing while keeping provider-specific implementation details and request-level decisions outside the model configuration boundary.
