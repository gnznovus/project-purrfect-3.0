# Structured Response Contract

## Purpose

The Structured Response Contract defines the boundary between LLM-generated structured data and Purrfect's deterministic application workflows.

LLMs may be used to interpret natural language, reason about tasks, and produce structured decisions. However, Purrfect must not rely on fragile free-form text when the result is consumed by deterministic application logic.

Structured responses provide a predictable contract that allows Purrfect to validate, process, and route model output safely.

---

## Responsibility

The Structured Response Contract is responsible for defining the requirements that apply whenever an LLM response is intended to be consumed as structured application data.

It defines:

* The expected structure of machine-readable model results.
* The boundary between model output and application processing.
* Validation requirements before structured data enters system workflows.
* Failure behavior when structured output is missing or invalid.
* Separation between generic response structure and domain-specific schemas.

---

## Structured Response Requirements

A structured LLM response must:

* Conform to the schema requested by the calling workflow.
* Be parseable by the application.
* Contain only the fields defined by the requested schema unless explicitly permitted.
* Use valid values for constrained fields.
* Preserve required data types.
* Include required fields.
* Avoid relying on natural-language interpretation when deterministic values are required.

Structured output must be treated as untrusted input until it has passed application-level validation.

---

## Schema Ownership

The Structured Response Contract does not own every schema used by Purrfect.

Domain-specific schemas belong to the component or workflow that requires them.

Examples include:

* Agent decision schemas.
* Planner schemas.
* Structured plans.
* Capability selection schemas.
* Tool-call schemas.
* Execution-related schemas.
* Other workflow-specific data contracts.

The calling workflow defines what information it requires.

Context Assembly provides the appropriate instructions and expected structure to the LLM.

The resulting response is validated before entering the corresponding workflow.

---

## Response Lifecycle

The general lifecycle is:

```
Workflow
    ↓
Define Required Structure
    ↓
Context Assembly
    ↓
LLM Provider Interface
    ↓
LLM
    ↓
Structured Response
    ↓
Provider Adapter
    ↓
Normalized Provider Result
    ↓
Response Processing
    ↓
Schema Validation
    ↓
Valid?
   ├── Yes → Continue Workflow
   └── No  → Handle Invalid Response
```

The LLM is responsible for producing the requested structure.

The application is responsible for validating that structure.

The application must not assume that a structurally invalid response is correct merely because the model produced it.

---

## Validation

Structured responses must be validated before they are used by deterministic system workflows.

Validation may include:

* Schema validation.
* Required field validation.
* Data type validation.
* Enum or constrained-value validation.
* Nested structure validation.
* Parameter validation.
* Business-rule validation where applicable.

Different validation responsibilities must remain separated.

For example:

* Schema validation confirms that the response has the correct structure.
* Parameter validation confirms that values are acceptable for the requested operation.
* Execution policy determines whether the requested operation is allowed.

A structurally valid response is not automatically authorized for execution.

---

## Invalid Structured Responses

If a structured response cannot be parsed or does not satisfy its required schema, Purrfect must not treat it as a successful result.

The system may:

* Request a corrected response from the same model.
* Retry the request when appropriate.
* Escalate to another model.
* Fail the current workflow.
* Return a safe failure to the appropriate higher-level component.

The selected recovery behavior depends on the workflow and failure type.

The Structured Response Contract does not own retry, model escalation, or workflow recovery policy.

---

## Structured Output and Tool Calls

Tool-call requests are treated as structured model outputs.

A model may request one or more tool operations using the tool-call contract provided by the current workflow.

The system must validate tool-call data before execution.

The general boundary is:

```
LLM
    ↓
Structured Tool Call
    ↓
Validate
    ↓
Execution Policy
    ↓
Execution Layer
```

The LLM does not directly execute the requested tool.

A valid tool-call structure only represents a request to perform an operation. It does not grant execution authority.

---

## Structured Output and User-Facing Responses

Not every LLM response must be structured.

Normal conversational responses may remain natural language.

Structured responses are required when the result is consumed by deterministic application logic.

For example:

```
User
    ↓
Chitchat Agent
    ↓
Normal Conversation
    ↓
Natural-Language Response
```

Whereas:

```
User
    ↓
Planner
    ↓
Structured Plan
    ↓
Validation
    ↓
Execution
```

The system should use structured output where deterministic processing requires it rather than forcing every LLM interaction into a rigid schema.

---

## Provider Independence

The Structured Response Contract describes the result Purrfect requires, not the provider-specific mechanism used to produce it.

Different providers may implement structured output differently.

The Provider-Specific Adapter is responsible for translating Purrfect's structured-output requirements into the provider's supported mechanism.

The resulting response must be normalized into the common Purrfect contract.

Provider-specific structured-output formats must not leak into unrelated core components.

---

## Relationship to Context Assembly

Context Assembly is responsible for determining and providing the structure required for the current LLM operation.

The Structured Response Contract defines the requirements that the resulting structured response must satisfy.

The relationship is:

```
Context Assembly
    ↓
Defines Required Structure
    ↓
LLM
    ↓
Structured Response
    ↓
Response Processing
    ↓
Validation
    ↓
Workflow
```

Context Assembly determines what the model needs to return.

Validation determines whether the model returned it correctly.

---

## Responsibility Boundaries

The Structured Response Contract owns:

* Requirements for machine-readable LLM responses.
* Structural validation boundaries.
* Common expectations for structured model output.
* The boundary between untrusted model output and deterministic workflows.

The Structured Response Contract does not own:

* Domain-specific business schemas.
* Prompt construction.
* Context assembly.
* Agent reasoning.
* Tool execution.
* Execution authorization.
* Retry policy.
* Provider failover.
* Model selection.
* User-facing response generation.

---

## Architectural Principle

> **LLM-generated structured output is untrusted input until validated by deterministic application code.**

The LLM may determine the content of a structured response, but Purrfect determines whether that response is structurally valid, safe to process, and authorized to continue through the relevant workflow.

Structured output provides the boundary that allows probabilistic LLM reasoning to interact safely with deterministic application logic.
