# Provider-Specific Adapter Boundary

## Purpose

The Provider-Specific Adapter Boundary isolates all provider-specific implementation details from Purrfect's core LLM architecture.

Each provider may expose different APIs, SDKs, request formats, response formats, authentication mechanisms, error structures, structured-output mechanisms, and tool-calling mechanisms.

Provider-specific adapters contain these differences so that the rest of Purrfect can communicate with LLM providers through the common LLM Provider Interface.

---

## Responsibility

A provider-specific adapter is responsible for:

* Communicating with the provider's API or SDK.
* Translating Purrfect's common LLM request into the provider's required request format.
* Translating provider responses into Purrfect's common response format.
* Extracting provider-reported usage metadata when available.
* Translating provider-specific errors into normalized provider errors.
* Handling provider-specific authentication requirements.
* Handling provider-specific API communication details.
* Translating provider-specific structured-output mechanisms.
* Translating provider-specific tool-calling mechanisms.

The adapter is responsible for **translation and provider communication**, not higher-level system decisions.

---

## Adapter Boundary

The core architecture communicates through the common LLM Provider Interface.

The general boundary is:

```
Purrfect Core
    ↓
LLM Provider Interface
    ↓
Provider-Specific Adapter
    ↓
Provider API / SDK
    ↓
Provider-Specific Response
    ↓
Provider-Specific Adapter
    ↓
Normalized Purrfect Response
    ↓
LLM Provider Interface
    ↓
Purrfect Core
```

The core architecture must not communicate directly with provider-specific APIs or SDKs.

---

## Request Translation

The adapter translates a provider-independent request into the format required by the provider.

For example:

```
Purrfect Request
    ↓
Common LLM Request
    ↓
Provider Adapter
    ↓
Provider-Specific Request
    ↓
Provider API
```

The adapter may translate:

* Message formats.
* Model identifiers.
* Structured-output requirements.
* Tool definitions.
* Tool-call formats.
* Generation parameters.
* Provider-specific request options.

The adapter must not change the semantic intent of the request.

---

## Response Translation

Provider responses must be normalized before they return to the core application.

The adapter may translate:

* Generated content.
* Structured model output.
* Tool-call requests.
* Usage metadata.
* Provider model identifiers.
* Provider-specific response metadata.

The normalized result must conform to the common LLM Provider Interface.

Provider-specific response formats must not leak into unrelated core components.

---

## Structured Output

Different providers may support structured output through different mechanisms.

Examples may include:

* Native structured response APIs.
* JSON schema support.
* Response format configuration.
* Prompt-based structured output.
* Other provider-specific mechanisms.

The adapter is responsible for translating Purrfect's structured-output requirements into the provider's supported mechanism.

The adapter does not define the schema required by the current workflow.

The schema is determined by the calling workflow and prepared through Context Assembly.

The adapter only ensures that the provider receives the appropriate provider-specific representation of that requirement.

---

## Tool Calling

Different providers may represent tool calls differently.

The adapter is responsible for translating between:

* Purrfect's common tool-call representation.
* The provider's tool definition format.
* The provider's tool-call response format.

The adapter does not execute tools.

The execution boundary remains:

```
LLM
    ↓
Tool Call
    ↓
Provider Adapter
    ↓
Normalized Tool Call
    ↓
Execution Layer
```

Tool execution, authorization, validation, and execution policy remain outside the adapter.

---

## Usage Metadata

When a provider reports usage metadata, the adapter is responsible for extracting and normalizing it.

Usage metadata may include:

* Input tokens.
* Output tokens.
* Total tokens.
* Cached tokens when available.
* Other provider-reported usage information.

The adapter must not fabricate usage information.

If a provider does not expose usage metadata, the normalized result may indicate that usage information is unavailable.

Optional usage estimation is outside the core adapter responsibility.

---

## Error Translation

Provider-specific errors must be translated into normalized errors defined by the LLM Provider Interface.

Examples include:

* Timeout.
* Temporary provider failure.
* Network failure.
* Rate limiting.
* Authentication failure.
* Invalid request.
* Unsupported capability.

The adapter reports the normalized failure.

It does not decide whether the system should:

* Retry.
* Switch providers.
* Escalate models.
* Cancel the workflow.
* Return a static fallback response.

Those decisions belong to higher-level provider failure and routing policies.

---

## Authentication

The adapter handles the provider-specific authentication mechanism required to communicate with the provider.

Examples may include:

* API keys.
* Local provider configuration.
* Authentication headers.
* Provider-specific credentials.

The adapter may consume credentials from the application's secure configuration system.

The adapter must not own long-term secret storage.

Secrets must remain outside source code and normal model configuration metadata.

---

## Provider Independence

Adding a new provider should require implementing a new adapter rather than modifying unrelated core components.

Conceptually:

```
Common LLM Provider Interface
    │
    ├── Provider A Adapter
    │
    ├── Provider B Adapter
    │
    └── Provider C Adapter
```

Each adapter may have completely different internal implementation details while exposing the same common contract to Purrfect.

---

## Provider-Specific Details Must Not Leak

Provider-specific details must remain inside the adapter boundary.

The following must not become dependencies of unrelated core components:

* Provider SDK types.
* Provider API response objects.
* Provider-specific error classes.
* Provider-specific tool-call structures.
* Provider-specific structured-output formats.
* Provider-specific authentication mechanisms.
* Provider-specific request formats.

Core components must depend on Purrfect's common contracts instead.

---

## Adapter vs Model Configuration

Model Configuration describes the model and its capabilities.

The Provider-Specific Adapter communicates with the provider.

The separation is:

```
Model Configuration
    ↓
What does the model support?
    ↓
Context Assembly
    ↓
What does this request require?
    ↓
LLM Provider Interface
    ↓
Provider Adapter
    ↓
How does this provider receive the request?
    ↓
Provider API
```

The adapter must not become the source of truth for model capabilities.

Model capability information belongs to Model Configuration and the Model Registry.

---

## Adapter vs Context Assembly

Context Assembly determines the content and requirements of the request.

The adapter translates that request into provider-specific API representation.

The separation is:

```
Context Assembly
    ↓
Build request
    ↓
Provider Interface
    ↓
Provider Adapter
    ↓
Translate request
    ↓
Provider API
```

The adapter must not decide:

* What context is relevant.
* What memory should be retrieved.
* What knowledge should be retrieved.
* What instructions the model should receive.
* What task the model should perform.

---

## Adapter vs Model Selection

Model Selection / Routing determines which model should handle a request.

The adapter communicates with the selected provider/model.

The separation is:

```
Model Selection / Routing
    ↓
Select Provider + Model
    ↓
LLM Provider Interface
    ↓
Provider Adapter
    ↓
Provider API
```

The adapter must not independently select a different model unless explicitly instructed by the higher-level routing system.

---

## Responsibility Boundaries

The Provider-Specific Adapter owns:

* Provider API communication.
* Provider SDK integration.
* Request translation.
* Response translation.
* Provider-specific structured-output translation.
* Provider-specific tool-call translation.
* Usage metadata extraction.
* Provider error normalization.
* Provider-specific authentication handling.

The Provider-Specific Adapter does not own:

* Context assembly.
* Prompt construction.
* Memory retrieval.
* Knowledge retrieval.
* Agent reasoning.
* Planning.
* Model selection.
* Model routing.
* Tool execution.
* Execution authorization.
* Retry policy.
* Provider failover policy.
* Cost calculation.
* Secret storage.

---

## Architectural Principle

> **The Provider-Specific Adapter is a translation and communication boundary, not a decision-making layer.**

Purrfect's core architecture defines what it needs from an LLM.

Context Assembly defines what the current request requires.

Model Configuration describes what the selected model supports.

The Provider Adapter translates those requirements into the provider's API and normalizes the provider's response back into Purrfect's common contracts.

Provider-specific complexity is allowed inside the adapter.

It must not leak beyond the adapter boundary.
