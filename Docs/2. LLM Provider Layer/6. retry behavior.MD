# Retry Behavior

## Purpose

Retry Behavior defines how Purrfect responds to temporary LLM provider failures that may succeed when the same request is attempted again.

Retries provide resilience against transient failures without allowing repeated attempts to block the system indefinitely.

Retry behavior is bounded and must remain separate from provider failover and higher-level workflow recovery.

---

## Responsibility

Retry Behavior is responsible for:

* Identifying failures that may be retried.
* Defining retry limits.
* Defining retry timing and backoff behavior.
* Preventing unbounded retry loops.
* Tracking retry attempts for the current LLM request.
* Returning the final failure when retry attempts are exhausted.

Retry Behavior does not decide the overall workflow response after retries are exhausted.

---

## Retryable Failures

Retries may be performed for failures that are likely to be temporary.

Examples include:

* Request timeout.
* Temporary network failure.
* Temporary provider unavailability.
* Rate limiting when retrying is permitted.
* Other explicitly classified transient provider failures.

A failure should only be retried when there is a reasonable expectation that another attempt may succeed.

---

## Non-Retryable Failures

Permanent failures must not be repeatedly retried.

Examples include:

* Invalid request.
* Invalid configuration.
* Authentication failure.
* Unsupported capability.
* Invalid model identifier.
* Other explicitly classified permanent provider failures.

Non-retryable failures should immediately proceed to Provider Failure Handling.

---

## Bounded Retries

Retry attempts must be strictly bounded.

The system must define:

* Maximum retry attempts.
* Maximum total retry duration when applicable.
* Maximum backoff duration.

A request must never retry indefinitely.

The retry counter applies to the current LLM request.

A new independent LLM request begins with a new retry policy unless the higher-level workflow explicitly defines otherwise.

---

## Retry Backoff

Retries should use a backoff strategy to avoid repeatedly sending requests to a provider that may be temporarily unavailable.

The initial implementation may use exponential backoff with an upper limit.

Conceptually:

```
Request
    ↓
Transient Failure
    ↓
Wait
    ↓
Retry
    ↓
Transient Failure
    ↓
Wait Longer
    ↓
Retry
    ↓
Retry Limit Reached
    ↓
Provider Failure Handling
```

Backoff duration must remain bounded.

The exact backoff implementation may vary by provider or failure type when necessary.

---

## Rate Limiting

Rate-limit failures may be retried when the provider indicates that retrying is appropriate.

When a provider supplies retry timing information, such as a retry-after duration, the retry policy may use that information.

The system must still enforce its own maximum retry count and maximum retry duration.

A provider-provided retry instruction must not override Purrfect's safety limits.

---

## Retry Request

A retry should represent another attempt to perform the same logical LLM operation.

The retry should preserve the original workflow requirements, including:

* Required model capabilities.
* Structured output requirements.
* Tool availability requirements.
* Relevant request context.

Provider-specific request details remain the responsibility of the Provider-Specific Adapter.

A retry must not silently change the semantic intent of the original request.

---

## Retry and Provider Failover

Retry Behavior and Provider Failure Handling are separate responsibilities.

The general flow is:

```
LLM Request
    ↓
Failure
    ↓
Retryable?
   ├── No → Provider Failure Handling
   │
   └── Yes
        ↓
      Retry
        ↓
    Retry Successful?
       ├── Yes → Continue Workflow
       │
       └── No
            ↓
      Retry Limit Reached?
         ├── No → Retry Again
         │
         └── Yes
              ↓
        Provider Failure Handling
              ↓
        Compatible Failover
              ↓
        Static Fallback if Necessary
```

Retry Behavior does not select the fallback provider or model.

Provider Failure Handling determines what happens after retry attempts are exhausted.

---

## Retry and Model Selection

A retry does not automatically imply that a different model should be selected.

The default behavior is to retry the same logical request using the same provider and model.

If repeated failures indicate that the selected provider or model is unavailable, the Provider Failure Handling or Model Selection / Routing system may perform a bounded failover to a compatible alternative.

The retry layer itself does not make model selection decisions.

---

## Retry and Idempotency

Retries must consider whether repeating the request can produce unintended side effects.

LLM requests themselves should normally be treated as non-executing operations.

However, a model response may later result in tool execution.

Tool execution must not be duplicated merely because an LLM request is retried.

The system must maintain a clear boundary between:

* Retrying an LLM request.
* Executing a tool.
* Retrying a tool execution.

Retrying an LLM request must not automatically repeat previously completed tool executions.

---

## Retry State

Retry attempts should be traceable.

Relevant metadata may include:

* Request ID.
* Execution ID.
* Provider.
* Model.
* Failure type.
* Retry attempt number.
* Maximum retry attempts.
* Backoff duration.
* Final outcome.

This information allows retry behavior to be observed and evaluated independently from the original provider failure.

---

## Responsibility Boundaries

Retry Behavior owns:

* Retry classification.
* Retry limits.
* Retry attempt tracking.
* Retry timing.
* Backoff behavior.
* Retry termination.

Retry Behavior does not own:

* Provider API communication.
* Provider-specific request translation.
* Model selection.
* Model routing.
* Provider failover.
* Tool execution.
* Execution authorization.
* Workflow recovery.
* User-facing failure responses.
* Static fallback responses.
* Cost calculation.

---

## Architectural Principle

> **Retry transient LLM provider failures within strict limits, then stop retrying and hand control to Provider Failure Handling.**

Retries exist to recover from temporary failures.

They must never become an infinite loop, silently change the intended operation, or bypass provider failover and execution safety boundaries.
