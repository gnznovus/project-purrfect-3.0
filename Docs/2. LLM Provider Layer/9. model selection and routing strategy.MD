# Model Selection / Routing Strategy

## Purpose

Model Selection / Routing determines which configured LLM model should handle a specific request.

Purrfect should not require every request to use the strongest or most expensive available model.

The system should begin with a configured default model and only move to a different model when the current workflow determines that the request requires capabilities, reasoning depth, or other characteristics better suited to another available model.

Model selection is bounded and must not become an uncontrolled recursive decision process.

---

## Responsibility

Model Selection / Routing is responsible for:

* Selecting the initial default model.
* Selecting an alternative model when escalation is required.
* Selecting a compatible model based on required capabilities.
* Using Model Registry metadata when evaluating candidates.
* Preserving required workflow capabilities during model changes.
* Supporting bounded model escalation.
* Preventing uncontrolled model-switching loops.

Model Selection / Routing does not perform the actual LLM request.

The selected model is passed to the LLM Provider Layer for execution.

---

## Default Model

Purrfect must have a configured default model.

The default model is the starting point for normal LLM workflows.

The general flow is:

```
User Request
    ↓
Context Assembly
    ↓
Default Model
    ↓
Process Result
```

The default model should be capable of handling the majority of normal Purrfect workflows.

The system should not require a routing decision before every request.

This avoids creating a circular dependency where a model is required to decide which model should be used before any model has been selected.

---

## Default-First Strategy

The default model acts as the initial model for the workflow.

If the request can be completed successfully using the default model, no additional model selection is required.

The system only considers escalation when there is a reason to do so.

Conceptually:

```
Request
    ↓
Default Model
    ↓
Sufficient?
   ├── Yes → Continue
   │
   └── No → Evaluate Escalation
                ↓
            Select Compatible Model
                ↓
            Continue
```

This keeps the common path simple while allowing more capable models to be introduced when required.

---

## Model Escalation

The default model may determine that the current task requires additional capabilities or stronger reasoning.

Escalation may be appropriate when:

* The task exceeds the model's supported capabilities.
* The model cannot reliably produce the required structured output.
* The task requires a capability unavailable to the current model.
* The task requires stronger reasoning than the current model is expected to provide.
* The current model repeatedly fails to complete the required workflow.
* The workflow explicitly requires a specialized model.

The decision to escalate may be produced as part of the model's structured response.

The escalation decision must be validated by deterministic application logic before another model is selected.

---

## Escalation Decision

A model may indicate that escalation is required through a structured result.

Conceptually:

```
Default Model
    ↓
Structured Result
    ↓
Requires Escalation?
   ├── No → Continue
   │
   └── Yes
        ↓
    Required Capabilities
        ↓
    Model Registry
        ↓
    Select Compatible Model
```

The model does not directly select an arbitrary provider or model identifier.

The application validates the escalation request and selects an eligible configured model.

This prevents the LLM from bypassing the Model Registry or directly controlling provider selection.

---

## Capability-Based Selection

Model selection must consider the capabilities required by the current workflow.

Examples include:

* Structured output.
* Tool calling.
* Multilingual understanding.
* Vision.
* OCR.
* Coding-specialized capabilities.
* Other supported model capabilities.

The Model Registry provides the metadata required to determine model compatibility.

A model that does not support a required capability must not be selected as a valid candidate.

---

## Stronger Model Escalation

Purrfect may use a stronger model when the default model determines that the task requires additional reasoning capability.

For example:

```
Default Model
    ↓
Understand Request
    ↓
Complex Task?
   ├── No → Continue
   │
   └── Yes
        ↓
    Request Escalation
        ↓
    Select Stronger Compatible Model
        ↓
    Continue Workflow
```

The exact definition of "stronger" belongs to model metadata and routing policy.

The system should not assume that a larger or more expensive model is automatically better for every task.

---

## Simple Requests

Simple requests should normally remain on the default model.

Examples may include:

* Basic conversation.
* Simple questions.
* Straightforward text generation.
* Simple structured decisions.

The system should avoid unnecessary escalation when the default model can reliably complete the task.

---

## Complex Requests

More complex requests may be escalated when the default model determines that additional capability or reasoning is required.

Examples may include:

* Complex multi-step planning.
* Difficult reasoning tasks.
* Complex structured planning.
* Tasks requiring specialized capabilities.
* Tasks where the default model repeatedly fails validation.

Escalation should remain bounded and should not automatically continue indefinitely.

---

## Model Selection and Model Registry

The Model Registry provides model metadata.

Model Selection / Routing uses that metadata to identify compatible candidates.

The separation is:

```
Model Registry
    ↓
Available Models
    ↓
Capabilities
Context Limits
Language Support
Availability
    ↓
Model Selection / Routing
    ↓
Selected Model
```

The Model Registry describes what models are available.

Model Selection / Routing determines which available model should handle the current request.

---

## Model Selection and Context Assembly

Context Assembly determines the requirements of the current LLM operation.

Model Selection / Routing uses those requirements to select a compatible model.

The relationship is:

```
Workflow
    ↓
Context Assembly
    ↓
Request Requirements
    ↓
Model Selection / Routing
    ↓
Compatible Model
    ↓
LLM Provider Interface
```

Context Assembly does not select the model.

Model Selection / Routing does not construct the complete request context.

---

## Model Selection and Provider Failure

Provider failure may require a temporary switch to another compatible model or provider.

This is different from normal model routing.

Normal routing:

```
Request
    ↓
Select Best Suitable Model
    ↓
Execute
```

Failure recovery:

```
Selected Model
    ↓
Failure
    ↓
Retry
    ↓
Failure Exhausted
    ↓
Select Compatible Alternative
    ↓
Execute
```

Normal routing determines the preferred model.

Provider Failure Handling determines whether a temporary fallback is required after failure.

---

## Model Selection and Provider Selection

Model Selection / Routing may select a model that belongs to a specific provider.

However, the core routing decision must remain independent of provider-specific API implementation.

The selected model is resolved through Model Configuration and the Model Registry.

The Provider-Specific Adapter handles communication with the selected provider.

The separation is:

```
Model Selection / Routing
    ↓
Select Model
    ↓
Model Configuration
    ↓
Provider Association
    ↓
LLM Provider Interface
    ↓
Provider Adapter
```

---

## Bounded Escalation

Model escalation must be bounded.

The system must prevent:

* Infinite escalation loops.
* Repeated escalation to the same model.
* Circular model switching.
* Uncontrolled model escalation chains.

A request should have a defined maximum escalation depth or equivalent bounded policy.

Once the escalation limit is reached, the current workflow must continue with the best available result or fail safely.

---

## Default Model as Decision Point

The default model may be used to determine whether escalation is necessary.

This avoids requiring a separate model-selection model for every request.

The architecture therefore follows:

```
Request
    ↓
Default Model
    ↓
"Can I handle this?"
   ├── Yes → Continue
   │
   └── No
        ↓
    Escalation Request
        ↓
    Application Validation
        ↓
    Model Registry
        ↓
    Select Stronger / Specialized Model
```

The default model does not have authority to bypass routing constraints.

The application remains responsible for validating and applying the final model selection.

---

## Model Routing and Tool Use

Tool requirements may influence model selection.

For example, a workflow requiring tool calling must select a model that supports tool calling.

The general flow is:

```
Workflow Requirements
    ↓
Required Tool Capabilities
    ↓
Model Selection
    ↓
Compatible Model
    ↓
Context Assembly
    ↓
LLM Request
```

The model does not directly decide whether a tool is safe to execute.

Tool selection and execution remain governed by the capability and execution architecture.

---

## Model Routing and Cost

Cost may be considered as a future routing factor.

The initial model routing strategy does not require dynamic cost optimization.

Usage metadata and pricing information may later provide data for evaluating:

* Model efficiency.
* Cost per task.
* Cost versus task success.
* Model performance.

Cost calculation remains separate from model selection.

Future routing policies may use historical cost data without embedding pricing logic into the LLM Provider Layer.

---

## Responsibility Boundaries

Model Selection / Routing owns:

* Default model selection.
* Model escalation decisions.
* Capability-based model selection.
* Selection of compatible configured models.
* Bounded model escalation.
* Validating model selection against Model Registry metadata.

Model Selection / Routing does not own:

* Model implementation.
* Provider API communication.
* Provider-specific request translation.
* Context assembly.
* Prompt construction.
* Agent reasoning.
* Tool execution.
* Execution authorization.
* Provider retry behavior.
* Provider failure recovery.
* Cost calculation.
* Pricing management.

---

## Architectural Principle

> **Purrfect starts with a configured default model and escalates only when the current workflow determines that another compatible model is required.**

The default model prevents a circular dependency in model selection.

The Model Registry provides the facts about available models.

The application validates escalation requests and selects a compatible model.

The LLM Provider Layer executes the request through the appropriate provider.

Model selection is bounded, capability-aware, and independent from provider-specific implementation details.
