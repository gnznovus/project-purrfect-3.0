# Token Usage Metadata

## Purpose

Token Usage Metadata defines how Purrfect receives and represents token usage information for individual LLM requests.

LLM providers may report how many tokens were consumed by a request. Purrfect should preserve this information as request-level metadata so it can later be used for observability, tracing, evaluation, and optional cost calculation.

Token usage is treated as factual request metadata when reported by the provider.

---

## Responsibility

Token Usage Metadata is responsible for:

* Capturing provider-reported token usage for individual LLM requests.
* Normalizing usage information across providers.
* Associating usage with the relevant provider and model.
* Preserving usage metadata for tracing and observability.
* Allowing usage to be aggregated across executions and conversations.
* Representing unavailable usage information without blocking normal processing.

Token Usage Metadata does not calculate cost.

---

## Request-Level Usage

Usage is collected independently for each LLM request.

For example:

```
LLM Request 1
    ↓
Input: 1,000 tokens
Output: 500 tokens

LLM Request 2
    ↓
Input: 2,000 tokens
Output: 800 tokens
```

Each request retains its own usage metadata.

Purrfect may later aggregate individual request usage into higher-level totals.

---

## Usage Metadata

When available, usage metadata may include:

* Input token count.
* Output token count.
* Total token count.
* Cached token count when supported.
* Provider identity.
* Model identity.
* Request identifier.
* Execution identifier.
* Conversation identifier.

The exact metadata available depends on the provider.

Provider-specific usage information may be preserved as optional metadata without becoming part of the required common contract.

---

## Provider-Reported Usage

Provider-reported usage is treated as the authoritative usage information for the corresponding request.

The Provider-Specific Adapter is responsible for extracting provider-reported usage and translating it into Purrfect's normalized usage representation.

The general flow is:

```
Provider API
    ↓
Provider Response
    ├── Generated Response
    └── Usage Metadata
            ↓
    Provider-Specific Adapter
            ↓
    Normalized Usage Metadata
            ↓
    Purrfect
```

The LLM itself is not responsible for reporting its own token usage.

Purrfect must not rely on model-generated content to determine actual token consumption.

---

## Usage Availability

Not every provider may expose token usage information in the same way.

When usage is available:

```
Usage Status: Reported
Input Tokens: Available
Output Tokens: Available
Total Tokens: Available
```

When usage is not available:

```
Usage Status: Unavailable
```

Missing usage information must not cause the LLM request or the overall workflow to fail.

Purrfect must not fabricate token usage values.

---

## Usage Accuracy

Usage metadata may be classified according to its source.

The primary source is:

```
Provider Reported
    ↓
Authoritative Request Usage
```

If a provider does not report usage, Purrfect may support future usage estimation through a separate mechanism.

Estimated usage must not be represented as provider-reported usage.

If estimation is introduced, the source must remain distinguishable from actual provider-reported usage.

For example:

```
Usage Source
├── Reported
├── Estimated
└── Unavailable
```

The initial MVP does not require usage estimation.

---

## Usage Aggregation

Individual request-level usage may be aggregated into higher-level metrics.

The aggregation hierarchy may include:

```
LLM Request
    ↓
Execution
    ↓
Conversation
    ↓
System
```

For example:

```
Request 1 → 1,500 tokens
Request 2 → 2,000 tokens
Request 3 → 500 tokens
             ↓
Execution Total → 4,000 tokens
```

Request-level usage remains the source of truth for all aggregation.

Aggregated usage must not replace the underlying request-level records when detailed tracing is required.

---

## Usage and Correlation

Usage metadata should be associated with the identifiers required to trace the request through Purrfect.

Relevant identifiers may include:

* Request ID.
* LLM Call ID.
* Execution ID.
* Conversation ID.

This allows usage to be correlated with:

* The originating user request.
* The execution workflow.
* The model used.
* The provider used.
* The final outcome.

---

## Usage and Cost Calculation

Token usage and pricing are separate concerns.

The LLM Provider Layer reports usage.

A separate Pricing Registry provides pricing metadata.

A separate Cost Calculator derives estimated cost.

The relationship is:

```
Provider
    ↓
Actual Token Usage
    ↓
Usage Metadata
    ↓
Cost Calculator
    ↑
Pricing Registry
    ↓
Estimated Cost
```

The Cost Calculator may use:

* Input token usage.
* Output token usage.
* Model identity.
* Provider identity.
* Pricing metadata.

Pricing information must not be embedded into token usage metadata.

The Provider Layer must not own cost calculation.

---

## Pricing Data

Pricing information is maintained separately from provider-reported usage.

For the initial implementation, pricing metadata may be manually maintained from the provider's official pricing documentation.

Conceptually:

```
Provider Documentation
    ↓
Pricing Registry
    ↓
Model Pricing Metadata
    ↓
Cost Calculator
```

Pricing changes should only require updating pricing metadata rather than modifying token usage or calculation logic.

The system must not assume that pricing information is permanently fixed.

---

## Local Models

Local LLM providers may expose usage metadata differently from hosted API providers.

If a local provider reports token usage, Purrfect should preserve it using the same normalized usage contract.

If the provider does not report usage, the usage status may remain unavailable.

Local model API cost may be represented as zero when appropriate, but infrastructure and hardware costs are outside the responsibility of token usage metadata.

---

## Usage and Model Routing

Token usage metadata may later be used as input for:

* Model performance evaluation.
* Model efficiency analysis.
* Context optimization.
* Model routing analysis.
* Usage monitoring.

Token Usage Metadata does not make routing decisions.

Model Selection / Routing may consume historical usage information when evaluating model efficiency, but the usage layer only reports and preserves usage facts.

---

## Responsibility Boundaries

Token Usage Metadata owns:

* Per-request usage representation.
* Provider-reported usage normalization.
* Usage availability status.
* Usage source classification.
* Usage correlation metadata.
* Request-level usage preservation.
* Usage aggregation support.

Token Usage Metadata does not own:

* Tokenization.
* Prompt construction.
* Context assembly.
* Model selection.
* Model routing.
* Provider pricing.
* Cost calculation.
* Billing.
* Provider API communication.
* Retry behavior.
* Provider failover.
* User-facing responses.

---

## Architectural Principle

> **Purrfect records actual token usage per LLM request when reported by the provider, preserves its source and availability, and treats request-level usage as the foundation for all later aggregation and cost calculation.**

Provider-reported usage is authoritative.

Pricing is maintained separately.

Cost is calculated separately.

Missing usage information never blocks normal system operation.
