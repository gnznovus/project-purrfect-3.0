# LLM Provider Interface

## Purpose

The LLM Provider Interface defines the common contract between Purrfect and any LLM provider.

It allows Purrfect to communicate with different providers through a consistent interface without coupling the core application to provider-specific APIs, SDKs, request formats, or response formats.

The interface represents the capabilities Purrfect requires from an LLM provider. Provider-specific implementation details remain isolated behind the Provider-Specific Adapter Boundary.

---

## Responsibility

The LLM Provider Interface is responsible for defining a provider-agnostic contract for:

* Sending requests to an LLM.
* Receiving generated responses.
* Supporting multilingual natural-language understanding and generation.
* Requesting structured model output.
* Receiving model-requested tool calls.
* Returning provider-reported usage metadata when available.
* Returning normalized provider errors.

The interface must provide enough common functionality for Purrfect's core workflows while remaining independent of any specific provider implementation.

---

## Core Capabilities

### 1. Text Generation

The interface must support general natural-language generation.

This is the basic operation used for:

* Conversational responses.
* Agent reasoning.
* Planning.
* Summarization.
* Other general LLM-generated content.

The interface does not define how a provider generates the response internally.

---

### 2. Multilingual Understanding

The interface must support models capable of understanding and generating the languages required by Purrfect.

The provider interface does not expose language-specific operations such as separate translation methods.

Language support is treated as a model capability and is described through Model Registry metadata.

Purrfect may use model capability metadata when selecting or escalating to an appropriate model.

The interface must support:

* Multilingual user input.
* Multilingual context.
* Mixed-language input when supported by the selected model.
* Responses in the appropriate user-facing language.
* Structured output independent of the natural language used in surrounding context.

---

### 3. Structured Output

The interface must support requests where Purrfect requires the model to produce structured data.

Structured output is used when model results enter deterministic system workflows.

Examples include:

* Agent decisions.
* Planner outputs.
* Structured plans.
* Capability selection.
* Tool-call requests.
* Other machine-readable model results.

The interface does not define individual business schemas.

Schemas are determined by the calling workflow and assembled through the appropriate context and response processing layers.

Provider adapters are responsible for translating the common structured-output requirement into the provider's supported mechanism.

---

### 4. Tool Calling

The interface must support model-generated requests to use tools.

The LLM Provider Layer is responsible only for communicating the tool-call request between Purrfect and the selected model.

It does not execute tools.

The execution responsibility remains with the Execution Layer.

The general flow is:

```
Purrfect Context Assembly
    ↓
LLM Provider Interface
    ↓
Provider / Model
    ↓
Tool Call Request
    ↓
Execution Layer
    ↓
Tool Result
    ↓
LLM Provider Interface
    ↓
Model
```

Tool availability and tool definitions are provided to the model through the appropriate context and capability systems.

The provider interface does not own tool implementations or execution policy.

---

### 5. Usage Metadata

The interface must support returning usage metadata for each individual LLM request when the provider exposes it.

Usage metadata may include:

* Input token count.
* Output token count.
* Total token count.
* Provider identity.
* Model identity.
* Other provider-reported usage information when available.

Provider-reported usage is treated as the authoritative usage information for that request.

If a provider does not expose usage information, the interface must allow the metadata to be unavailable without preventing normal request processing.

Usage metadata may later be aggregated by:

* LLM request.
* Execution.
* Conversation.
* System.

Cost calculation is outside the responsibility of the LLM Provider Interface.

---

### 6. Normalized Errors

The interface must provide provider-independent error information.

Provider-specific errors must be translated into normalized errors before being returned to Purrfect's core workflows.

Normalized errors may represent conditions such as:

* Timeout.
* Temporary provider failure.
* Network failure.
* Rate limiting.
* Authentication failure.
* Invalid request.
* Unsupported capability.
* Other provider failures.

The interface does not decide how the overall workflow should respond to the failure.

Retry policy, provider failover, and final failure handling are defined separately.

---

## Responsibility Boundaries

The LLM Provider Interface owns:

* The common contract for LLM communication.
* Core LLM capabilities required by Purrfect.
* Provider-independent request and response boundaries.
* Provider-reported usage metadata.
* Normalized provider errors.

The LLM Provider Interface does not own:

* Context construction.
* Prompt or instruction strategy.
* Agent reasoning.
* Planning.
* Tool execution.
* Execution authorization.
* Business logic.
* Memory management.
* Knowledge retrieval.
* Response assembly.
* Cost calculation.
* Model selection.
* Provider-specific implementation details.

---

## Provider Independence

The core Purrfect architecture must communicate with LLM providers through the common interface rather than directly through provider APIs or SDKs.

Provider-specific behavior must remain behind the Provider-Specific Adapter Boundary.

The architecture must allow providers to be:

* Added.
* Removed.
* Replaced.
* Temporarily failed over.

without requiring unrelated core components to change.

---

## Capability Extensibility

The initial interface focuses on the core capabilities required for the Purrfect MVP:

* Text generation.
* Multilingual understanding.
* Structured output.
* Tool calling.
* Usage metadata.
* Normalized errors.

Advanced capabilities are not required to be part of the initial common interface.

Potential future capabilities may include:

* Vision.
* OCR.
* Multimodal input.
* Coding-specialized model capabilities.
* Other provider-specific or specialized model capabilities.

Future capabilities should be added as explicit extensions rather than unnecessarily expanding the core interface.

---

## Architectural Principle

> **The LLM Provider Interface defines what Purrfect requires from an LLM provider, not how the provider implements it.**

The interface should remain small enough to support multiple providers while providing all core capabilities required by Purrfect's AI workflows.

Provider-specific details belong to provider adapters.

Task-specific requirements belong to Context Assembly.

Model capability information belongs to the Model Registry.

Execution belongs to the Execution Layer.
