# Provider Failure Handling

## Purpose

Provider Failure Handling defines how Purrfect responds when an LLM provider cannot successfully complete a request after the applicable retry policy has been exhausted, or when a failure is determined to be non-retryable.

The goal is to prevent provider failures from becoming uncontrolled system failures while ensuring that unsuccessful operations are never represented as successful results.

---

## Responsibility

Provider Failure Handling is responsible for:

* Receiving normalized provider failures.
* Determining the next recovery stage after retry exhaustion.
* Attempting bounded temporary failover when a compatible alternative is available.
* Preventing repeated provider failover loops.
* Returning a normalized final failure when no viable provider remains.
* Triggering a safe static fallback response when the system cannot obtain an LLM response.

Provider Failure Handling does not decide how the user's overall workflow should proceed after the final failure.

---

## Failure Lifecycle

The general failure hierarchy is:

```
LLM Request
    ↓
Primary Provider
    ↓
Failure
    ↓
Retry Policy
    ↓
Retry Exhausted
    ↓
Compatible Provider / Model Available?
   ├── Yes → Temporary Failover
   │            ↓
   │        Request Successful?
   │           ├── Yes → Continue Workflow
   │           └── No → Continue Bounded Failover
   │
   └── No
        ↓
  Static Fallback Response
        ↓
       User
```

The system must never remain indefinitely inside the failure recovery process.

---

## Non-Retryable Failures

A failure classified as permanent may bypass retry behavior and proceed directly to Provider Failure Handling.

Examples include:

* Invalid request.
* Invalid configuration.
* Authentication failure.
* Unsupported capability.
* Invalid model identifier.
* Other failures that are unlikely to succeed through another attempt using the same configuration.

Provider Failure Handling determines whether an alternative compatible provider or model can be used.

---

## Temporary Provider Failover

When the primary provider cannot complete a request after retry attempts are exhausted, Purrfect may temporarily fail over to another compatible provider or model.

The fallback must satisfy the requirements of the original request.

Compatibility may include:

* Required model capabilities.
* Structured output support.
* Tool-calling support.
* Required language support.
* Other workflow-specific requirements.

Failover must not silently reduce required capabilities.

For example, if the original workflow requires structured output and tool calling, a fallback that cannot provide those capabilities must not be selected as a valid replacement.

---

## Bounded Failover

Provider failover must be strictly bounded.

The system must prevent:

* Infinite provider switching.
* Repeated attempts against the same failed provider.
* Circular provider fallback.
* Unbounded fallback chains.

Each provider/model should have a bounded attempt policy for the current request.

A provider that has already failed for the current request should not be repeatedly selected unless explicitly allowed by the failure policy.

---

## Failover and Model Selection

Provider Failure Handling may request an alternative provider or model that satisfies the original request requirements.

It does not independently redefine the user's task.

The relationship is:

```
Original Request
    ↓
Required Capabilities
    ↓
Model Selection / Routing
    ↓
Primary Provider + Model
    ↓
Failure
    ↓
Provider Failure Handling
    ↓
Compatible Alternative
    ↓
Retry / Failover
```

The fallback must preserve the original logical operation.

---

## Final Failure

If no compatible provider or model can successfully complete the request, the system must produce a normalized final failure.

The final failure must clearly indicate that the requested LLM operation was not completed.

The system must not:

* Fabricate an LLM response.
* Fabricate tool results.
* Fabricate execution results.
* Claim that an action was completed.
* Treat an unavailable provider as successful.

The final failure should remain traceable to the original request.

---

## Static Fallback Response

When all viable providers and models fail, Purrfect may return a predefined static fallback response.

The static fallback exists as the final communication safety net when the system cannot obtain a valid LLM-generated response.

Examples may include:

> "I'm temporarily unable to process that request right now. Please try again in a moment."

The static fallback must:

* Clearly communicate that processing was unsuccessful.
* Avoid claiming task completion.
* Avoid fabricating information.
* Avoid fabricating tool or execution results.
* Remain safe when the original request cannot be processed.

Static fallback responses should be intentionally limited and should not attempt to reproduce the functionality of the unavailable LLM.

---

## Static Fallback and Workflow State

A static fallback response does not imply that the user's requested operation was completed.

The system must preserve the distinction between:

* Request received.
* Request processed successfully.
* Request partially processed.
* Request failed.
* Request unavailable due to provider failure.

If an operation required tool execution and the LLM provider failed before a valid execution plan was produced, the system must not report the operation as completed.

---

## Failure Loop Prevention

Provider failure recovery must prevent circular recovery paths.

For example:

```
Provider A
    ↓ Failure
Provider B
    ↓ Failure
Provider A
    ↓ Failure
Provider B
    ↓ Failure
∞
```

This must never occur.

Each recovery attempt must be bounded by the request's failure policy.

Once the configured recovery limits are exhausted, the system must terminate the provider recovery process.

---

## Failure Metadata

Provider failures should retain enough metadata for tracing and diagnosis.

Relevant information may include:

* Request ID.
* Execution ID.
* Conversation ID.
* Provider.
* Model.
* Failure type.
* Retry attempts.
* Failover attempts.
* Providers/models attempted.
* Final outcome.
* Whether a static fallback was used.

Provider-specific error details may be preserved as diagnostic metadata without becoming dependencies of the core workflow.

---

## Observability

Provider failure events must be visible through the system's tracing and observability mechanisms.

A failure should be traceable across:

```
Request
    ↓
Provider Attempt
    ↓
Retry Attempts
    ↓
Failover Attempts
    ↓
Final Outcome
```

This allows the system to distinguish between:

* Primary provider failure.
* Retry exhaustion.
* Failover success.
* Failover exhaustion.
* Final static fallback.

---

## Responsibility Boundaries

Provider Failure Handling owns:

* Post-retry provider failure recovery.
* Temporary provider failover.
* Failover attempt limits.
* Failure loop prevention.
* Final provider failure determination.
* Static fallback triggering.

Provider Failure Handling does not own:

* Provider API communication.
* Provider-specific request translation.
* Timeout detection.
* Retry policy.
* Model configuration.
* Model selection.
* Agent reasoning.
* Planning.
* Tool execution.
* Execution authorization.
* User workflow decisions.
* Cost calculation.

---

## Architectural Principle

> **Provider failure recovery must be bounded, capability-aware, and honest about failure.**

Purrfect should first retry transient failures within defined limits.

When retries are exhausted, it may temporarily fail over to a compatible provider or model.

If all viable recovery paths fail, Purrfect must terminate the recovery process and provide a safe static response without fabricating success, information, or execution results.
